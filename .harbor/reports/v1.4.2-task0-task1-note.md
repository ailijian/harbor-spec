## Task 1.0 Design Record

### Compared Options

#### Option A: 泛化现有 worker
- 做法：直接把 `process_file_worker` 从 Python 专用改成多语言 worker，并在 worker 内分别解析 Python / TypeScript。
- 优点：复用现有并行写库流程，IndexBuilder 改动集中。
- 缺点：如果只做 worker 泛化，Python `FunctionContract` 与 TypeScript `ContractSubject` 仍会在写库阶段分叉，后续 `meta` 兼容与 JSON 快照导出容易继续散落在多个位置。

#### Option B: 保留 Python 路径并补 TS persistence path
- 做法：保留现有 Python-only build 流程，再额外增加一条 TypeScript 专用发现、解析、写库路径。
- 优点：初始编码量看起来最少。
- 缺点：会形成双轨持久化路径；`entries` 写入、快照导出、迁移兼容与测试将重复维护，不符合 generalized persistence 目标。

#### Option C: 抽 normalization / entry adapter 层
- 做法：保留现有 `entries` 表与主写库流程，补一层很薄的跨语言 entry normalization，把 Python `FunctionContract` 与 TypeScript `ContractSubject` 都归一化为统一 entry payload，再走同一持久化路径。
- 优点：最小侵入、对 Python 零回归最友好、后续可继续扩展 `interface/type`、Zod、`contract_hash`。
- 缺点：需要同步调整 worker、`IndexBuilder` 快照导出与 JSON/SQLite 兼容细节。

### Chosen Direction
- 选择 Option C，并在实现上只引入最小必要泛化：
- 保留现有 `entries` 表结构：`id/file_path/signature_hash/body_hash/contract_hash/meta`。
- 保留 Python 既有 `meta` 字段与旧消费路径。
- 将 `target_id`、`legacy_func_id`、`language`、`symbol_kind`、`qualified_name`、`visibility`、`end_lineno`、`contract_source_*` 等 TS 身份与摘要信息作为 additive `meta` 持久化。
- 让 `IndexBuilder` 通过 registry 同时发现 Python / TypeScript 文件，并把两类 subject 统一写入 SQLite 和 `l3_index.json`。
- 不改变 accepted baseline artifact 的读取、比较与 CI truth 语义。
- 不在 Task 1 中扩大 TS blocking gate，只完成“可持久化、可作为 baseline 基础”。

### Immediate Implementation Plan
1. 增加跨语言 entry normalization helper。
2. 将 `process_file_worker` 改为支持 Python / TypeScript 两类文件。
3. 让 `IndexBuilder._iter_files_by_enabled_adapters()` 正式纳入 TypeScript discovery。
4. 保持 `HarborDB` schema 不变，但放宽 `meta` 的 additive 持久化与 JSON migration 兼容。
5. 补齐 Task 1 对应测试：TS subject 入库、identity metadata、hashes、Python 回归不破坏。
