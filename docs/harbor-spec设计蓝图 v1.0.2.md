# Harbor-spec v1.0.2：主动上下文引擎设计蓝图（去中心化落地版）

> 一句话定位：
> **Harbor-spec =「像 Git 管代码仓库一样，自动管理 vibe coding 的上下文仓库」**
> —— 以 L3 Docstring 为原子事实、以 DDT 测试为可执行规范、以 L2/Diary 为可计算视图，配合 CLI + Sync Engine + AI 规则，为 AI 驱动开发（vibe coding）提供一个**强一致、可回溯、可治理**的主动上下文层。

> 版本说明：v1.0.2 在 v1.0.1 的架构与不变式基础上，**引入去中心化索引、DDT 韧性增强、Diary 轮转与 AI 语义审计**，目标是更适合真实团队落地。

---

## 版本 Changelog（相对 v1.0.1）

1. **索引去中心化（Decentralized Index）**

   * `l3_index` 及相关索引从“入库文件”降级为 **Gitignored 缓存**：

     * 统一由 `harbor build-index` / `harbor status` 动态构建；
     * 彻底避免多人协作时的 `l3_index.json` 合并冲突地狱。
   * 不变：**真相源仍然是代码中的 L3 Docstring**。

2. **DDT 韧性增强（Resilient DDT）**

   * 引入 **Contract / Decoration 分区 + 语义哈希**：

     * 仅当“契约区”变更时才强制 `l3_version` 升级；
   * 新增 **Smart Linking & CLI 更新**：

     * 支持 `strategy="latest"` 这种“自动跟随最新版本”的测试绑定；
     * 同时**强制规定：L3 严格级别为 `strict` 的 Public/Critical API 禁用 `latest`，必须显式绑定版本号**；
     * `harbor ddt update` 提供交互式升级测试绑定。

3. **AI 语义审计（Semantic Audit）**

   * 新增命令 `harbor audit --semantic`，在 CI 的**软检查阶段**调用 LLM：

     * 检查“代码实现是否与 Docstring 契约一致”；
     * 标记为 `POSSIBLE_SEMANTIC_DRIFT`；
   * **明确策略：语义审计永远是 soft-check，不作为 v1.0.2 的硬阻塞条件。**

4. **Diary 轮转与轻量化**

   * 将单一 `DEVELOPMENT_DIARY.jsonl` 拆分为：`specs/diary/YYYY-MM.jsonl`；
   * Diary entry 简化，更多依赖 `commit_hash` 关联详细 diff；
   * 保留 `importance / visibility` 字段以控制噪音与隐私。

5. **战线收敛**

   * v1.0.2 **仅正式支持 Python 语言适配器**，作为唯一 Reference 实现；
   * 多语言适配进入 roadmap，暂不承诺交付时间。

## 0. 设计宗旨与 Git 类比（架构层保持不变）

### 0.1 设计宗旨（架构视角）

Harbor-spec v1.0.2 解决四个核心问题：

1. **上下文漂移（Context Drift）**

   * 代码、Docstring、README、历史决策之间容易不一致；
   * LLM 只看到一部分上下文就开始“拍脑袋”。

2. **文档“为人写”不适配 AI**

   * `/docs` 里一堆长文档，人类都不看，更别说 LLM；
   * Harbor 要提供的是 **结构化、可索引、可计算的上下文视图**。

3. **TDD 在 vibe coding 下落地困难**

   * 实际流程：AI 先写实现 → 再补契约/测试；
   * Harbor 用 **L3 契约 + DDT** 把这个过程“重新规整到可治理轨道”。

4. **团队级治理缺位**

   * 单靠个人自觉 + IDE 插件不可靠；
   * 需要 repo 级、CI 级的硬约束与指标。

### 0.2 Git 类比与能力边界

* Git 管的是：**源码快照与提交历史**；
* Harbor 管的是：**主动上下文（L3/L2/Diary）的快照与演进**。

| Git              | Harbor-spec v1.0.2                            |
| ---------------- | --------------------------------------------- |
| 代码文件             | L3 Docstring（代码内契约）                           |
| `git status`     | `harbor status`（上下文状态）                        |
| `git diff`       | `harbor diff context`（契约/L2/Diary diff）       |
| `git log`        | `harbor log context`（上下文变更历史）                 |
| commit hook / CI | pre-commit + CI 中的 `harbor sync/*` + `health` |

**能力边界（要写死的前提）：**

* v1.0.2 提供的是：

  * **结构一致性保障**（代码 ↔ L3 ↔ L2/Diary）；
  * **可观测性**（健康度、变更日志、测试覆盖）；
  * **AI 友好的上下文 API 与软审计**。
* v1.0.2 不负责：

  * 业务逻辑永远正确；
  * 文案/事实 100% 准确；
  * 替代代码评审 & 深度测试。

## 1. 四层上下文模型与不变式（与 v1.0.1 一致）

### 1.1 四层模型

1. **L1 – Constitution（宪法）**

   * 位置：`/.cursor/rules/harbor-spec-L1-Constitution.mdc`
   * 定义工程底线与 AI 行为准则。

2. **L2 – Anchor（锚点 / 模块 README）**

   * 位置：`modules/<name>/README.md`
   * 由 Harbor 从 L3 & Diary & DDT 生成，**只读视图**。

3. **L3 – Atomic Fact（原子事实 / Docstring 契约）**

   * 位置：代码内部 Docstring；
   * 是行为与契约的**单一事实来源（SSOT）**。

4. **L-Memory – Diary（开发日记 / 演进记忆）**

   * 真相源：`specs/diary/YYYY-MM.jsonl`；
   * Markdown 镜像：`specs/DEVELOPMENT_DIARY.md`（可选，只读）。

### 1.2 不变式（Invariants）

1. **L3 代码 ↔ Docstring 强一致（结构级 Hard Invariant）**

   * 任何受管 L3 函数，签名或函数体变更 → Docstring 必须更新；
   * `harbor sync l3 --check` 在任何 profile 下**一旦发现不一致就 fail**；
   * 不依赖索引是否入库。

2. **L2/Diary 是视图，不是事实源**

   * 任何视图文件都带有 `AUTO-GENERATED BY HARBOR` 头；
   * 真相源：

     * L3 → 代码 Docstring；
     * Diary → `specs/diary/*.jsonl`；
   * 手动改视图会被识别并提示修复。

3. **Public API 必须有 DDT 覆盖（配置依赖的 Hard Gate）**

   * Public 函数最低要求：`DDT_MINIMAL`（至少 1 正常 + 1 异常路径）；
   * 与 L3 通过 `@harbor_ddt_target` 或等价机制绑定；
   * 在 `profile=full_harbor && sync.mode=strict` 下：

     * Public 无 DDT_MINIMAL → fail；
     * 严格 API 的测试版本与 L3 不匹配 → fail。

4. **Harbor 以模块/路径为单位渐进启用**

   * 通过 `.harbor/config.yaml` 的 `enabled_paths`/`exclude_paths` 控制；
   * 支持 observe_only → enforce_l3 → full_harbor 渐进演进。

5. **索引是衍生品，可重建**

   * `l3_index` 等索引是由代码 + Diary 动态生成的“语义视图”，**不是真相源**；
   * 推荐作为 `.harbor/cache` 下的构建产物，不入库；
   * CI/本地使用 `harbor build-index` 或等价命令快速重建。

6. **语义一致性由多方共同保障**

   * Harbor 负责结构一致 & DDT 绑定；
   * 语义正确性依赖：

     * 良好的测试实践；
     * 代码评审；
     * **可选的 AI 语义审计（soft-check）。**

## 3. L3 层：Docstring 作为原子事实 + 语义哈希

### 3.1 L3 严格度分级（沿用 v1.0.1）

通过 `@harbor.l3_strictness` + config 控制 L3 要求强度：

* `light`：轻量 L3，适合内部小 helper；
* `standard`：默认 L3，适合大部分 internal；
* `strict`：严格 L3，**适用于 Public/Critical API**，要求完整契约 + DDT_MINIMAL。

配置示例：

```yaml
l3:
  enabled: true
  enabled_paths:
    - "modules/*/src"
  exclude_paths:
    - "legacy/**"
  strictness_defaults:
    public: "strict"
    internal: "standard"
  overrides:
    - path: "modules/legacy/**"
      strictness: "light"
```

### 3.2 Docstring Contract / Decoration 区分

为解决“改个标点也触发版本升级”的痛苦，v1.0.2 在解析 Docstring 时将其拆分为：

1. **Contract Area（契约区）**

   * 包含：

     * `summary / 功能 / 使用场景 / 依赖`
     * `Args / Returns / Raises`
     * `@harbor.*` tags（scope / idempotency / strictness 等）
   * **变更后果：**

     * 触发 `contract_hash` 变化；
     * 在 L3 严谨配置下 → 需要 `l3_version++`，触发 DDT 关注。

2. **Decoration Area（修饰区）**

   * 包含：

     * 示例代码；
     * 扩展说明；
     * 格式排版、空行等。
   * **变更后果：**

     * 不改变 `contract_hash`；
     * `docstring_raw_hash` 变化但 `contract_hash` 不变 → 即视为“装饰变更”，**不要求升级 `l3_version`**。

索引中保留两个 hash 字段（示意）：

```jsonc
{
  "id": "modules.auth.login.login_user",
  "contract_hash": "sha256:...",   // 只基于契约区
  "docstring_raw_hash": "sha256:..."  // 基于整个 docstring
}
```

Sync 规则（简化版）：

* `body_hash/signature_hash` 变化：

  * 严格要求：开发者/AI 应同步更新契约区 → `contract_hash` 变化 → `l3_version++`；
* 只有 Decoration 变化：

  * `contract_hash` 不变 → `l3_version` 可以不动。

**注意：**
Harbor 可以在 `harbor sync l3 --check` 时，提示“实现变了但契约没变”，由 CA 决定是否强制提升版本。

## 4. 配置与 Profile（延续 v1.0.1）

整体结构延续 v1.0.1，只强调新增字段：

```yaml
schema_version: "1.0.2"

project:
  name: "awesome-service"
  language: "python"
  profile: "enforce_l3"    # observe_only | enforce_l3 | full_harbor

code_roots:
  - "modules/*/src"

test_roots:
  - "modules/*/tests"

l3:
  enabled: true
  enabled_paths:
    - "modules/*/src"
  exclude_paths:
    - "legacy/**"
  strictness_defaults:
    public: "strict"
    internal: "standard"
  overrides:
    - path: "modules/legacy/**"
      strictness: "light"

l2:
  enabled: true
  auto_regen: true

diary:
  enabled: true
  dir: "specs/diary"
  min_importance_to_auto_log: "normal"  # trivial | normal | high | critical
  default_visibility: "internal"        # internal | repo | public

ddt:
  minimal_required_for_public: true
  treat_missing_as_error_in_strict_profile: true
  # 严格级别函数禁止使用 latest 策略
  forbid_latest_for_strict: true

sync:
  mode: "relaxed"              # relaxed | strict

health:
  thresholds:
    min_public_ddt_coverage: 0.8
    max_context_debt: 10
```

Profile 三档行为与之前一致，此处略。

## 5. DDT：绑定策略与维护工具（融合版）

### 5.1 绑定方式（强约束 + Smart Linking）

装饰器两种用法：

```python
# 方式 A：严格模式（适用于 strict 级别 / Public / Critical API）
@harbor_ddt_target(
    func="modules.auth.login.login_user",
    l3_version=3
)

# 方式 B：松散模式（仅允许用于 non-strict 函数）
@harbor_ddt_target(
    func="modules.auth._helper_something",
    strategy="latest"
)
```

**策略（写死的 v1.0.2 规则）：**

* 当函数的 `l3_strictness = "strict"` 或 scope 为 public/critical 时：

  * 使用 `strategy="latest"` **视为配置错误**，`harbor sync --ci` 直接 fail；
  * 必须显式绑定 `l3_version`（例如 `l3_version=3`）。
* 对于 `standard`/`light` 严格度的 internal 函数：

  * 可以选择 `strategy="latest"`，降低维护成本；
  * 仍然可选用显式版本绑定。

### 5.2 `harbor ddt update`：交互式维护

为减轻 version 升级维护负担，v1.0.2 提供：

```bash
harbor ddt update [--func <id>] [--module <path>]
```

流程示例：

```text
[Harbor] 检测到 L3 契约版本变更：
  - modules.auth.login.login_user: v3 -> v4
  - 契约变更摘要：新增可选参数 `timeout`，默认值为 None

[Harbor] 关联测试：
  1) test_login_user_valid_credentials (modules/auth/tests/test_login.py)
  2) test_login_user_invalid_password_raises (modules/auth/tests/test_login.py)

这些测试在新契约下是否仍然有效？
  [1] 全部仍然有效 (Yes)
  [2] 需要我后续手动检查 (No)
  [3] 进入审计模式（列出建议断言）(Audit)

> 1

[Harbor] 已自动将上述测试中的 l3_version 从 3 更新为 4。
```

* 对 strict 函数，这个流程是 **刚需**；
* 对 non-strict 函数，若使用 `strategy="latest"`，则不会进入 version 更新，维护成本更低。

### 5.3 DDT 等级与 CI 门槛（与 v1.0.1 一致）

* `DDT_NONE`：无绑定测试；
* `DDT_MINIMAL`：1 正常 + 1 异常；
* `DDT_FULL`：覆盖所有关键分支（后续扩展）。

在 `profile=full_harbor && sync.mode=strict` 下：

* 对 `scope=public` 且 `l3_strictness=strict` 的函数：

  * 若 DDT 状态 < `DDT_MINIMAL` → fail；
  * 若使用 `strategy="latest"` → fail（违背 v1.0.2 策略）。

## 6. L2 层：自动模块锚点（轻量视图）

保持 v1.0.1 设计：由 L3 + DDT + Diary 聚合生成，强调几点：

1. **L2 是“稳定摘要”，不是长篇叙事**

   * 目标：给新人、AI Router、审查者一个模块级鸟瞰；
   * 使用 `l2_meta.json` 控制字段顺序和展示策略，避免小变动导致 README 大范围 diff。

2. **允许 embed 简短质量统计**

   * 公共 API 数量、DDT 覆盖率、最近 Diary 计数等。

生成流程依旧：

```bash
harbor gen l2 --module modules/auth
```

或由 `harbor sync` 自动触发。

## 7. L-Memory：Diary 轮转 + 噪音 & 隐私控制

### 7.1 存储结构

* 路径：`specs/diary/YYYY-MM.jsonl`
* 每行一个 `DiaryEntry`，示例（v1.0.2 简化版）：

```jsonc
{
  "ver": 1,
  "ts": "2025-12-15T10:00:00Z",
  "author": "CA / AI",
  "type": "bugfix",          // feature | bugfix | refactor | incident | chore
  "importance": "high",      // trivial | normal | high | critical
  "visibility": "internal",  // internal | repo | public
  "scope": ["modules.auth"],
  "functions": ["modules.auth.login.login_user"],
  "summary": "修复 login_user 未捕获 DBError 导致 500 的问题。",
  "reason": "违反 L1 规则：API 不得返回 500。",
  "ref_commit": "abc123"
}
```

### 7.2 轮转与聚合策略

* 写入策略：

  * 永远写入“当前月”的 JSONL 文件；
* 读取策略：

  * 默认聚合“当前月 + 上一月”；
  * 如需追溯更久，调用方需显式指定时间范围。

### 7.3 噪音控制

* 自动生成 Diary 候选时，结合：

  * 变更类型（bugfix / incident 等）；
  * 影响范围（Public API / Critical 模块）；
* 只对 `importance >= min_importance_to_auto_log` 的事件生成草稿；
* 允许 CA 在 IDE / CLI 中：

  * 调整 importance；
  * 调整 visibility（防止信息泄露到外部仓库）。

## 8. Sync Engine v1.0.2：增量 & 无冲突索引

### 8.1 核心原则

1. **只从代码 & Diary 推导索引与视图**；
2. **索引作为缓存，不入库**；
3. **尽可能增量扫描，避免大仓库性能问题**。

### 8.2 典型命令与流程

1. **本地开发**

   * 开发者运行：

     ```bash
     harbor status       # 内部会触发增量 build-index
     harbor sync l3 --check
     ```
   * `l3_index.json` 更新到 `.harbor/cache`，不产生 Git diff。

2. **pre-commit**

   ```bash
   harbor sync --pre-commit
   ```

   * 行为包含：

     * 增量 build-index；
     * 检查 L3 一致性；
     * 生成/更新 L2 README；
     * 写入当前月 Diary。

3. **CI**

   ```bash
   harbor build-index    # 全量重建索引（通常 <5s）
   harbor sync --ci      # 包含 L3/L2/Diary/DDT 检查
   harbor audit --semantic  # 软审计（不阻塞构建）
   harbor report --format markdown > harbor_report.md
   ```

## 9. AI 语义审计（Semantic Audit）——永远软检查

### 9.1 配置与规则

* 审计规则存放于：`.harbor/semantic_guard.yaml`，包括：

  * 需要审计的模块/函数 scope；
  * 允许的风险等级；
  * 使用的 LLM provider / 模型名称（不在本蓝图内展开）。

### 9.2 命令：`harbor audit --semantic`

触发模式：

```bash
harbor audit --semantic [--since-commit <sha>] [--module <path>]
```

行为：

1. 收集本次变更中 L3 有变动的函数；
2. 对每个函数：

   * 提取：函数实现 + L3 契约（Contract Area）；
   * 构造审计 Prompt，让 LLM 检查：

     * Args/Returns/Raises 是否与实现匹配；
     * 功能描述是否严重偏离实现。
3. 输出结果到：

   * CI 日志；
   * 或者生成 Markdown 报告。

### 9.3 策略（重要）：

* **v1.0.2 明确规定：`harbor audit --semantic` 只作为 soft-check**：

  * 可以将结果转为 PR 评论；
  * 可以标记为 `POSSIBLE_SEMANTIC_DRIFT`；
  * **不能作为构建 fail 的硬门槛**（避免 LLM 误判阻断流程）。
* 真正是否修改，由人类（CA / Reviewer）决定。

## 10. CLI 命令族（汇总 v1.0.2）

在 v1.0.1 基础上补充去中心化 & DDT & Audit：

* 初始化：

  * `harbor init [--profile <name>] [--with-pre-commit] [--with-github-actions]`
* 索引与同步：

## 13. 典型工作流（v1.0.2 合并版）

### 13.1 新项目（Python-only）快速接入

1. `harbor init --profile full_harbor --with-pre-commit --with-github-actions`
2. 开发者/AI 写代码 + Docstring（strict/standard/light 区分）；
3. 本地：

   * `harbor status` → 自动 build-index；
   * `harbor sync --pre-commit`；
4. CI：

   * `harbor build-index`
   * `harbor sync --ci`
   * `harbor audit --semantic`（软审计）
   * `harbor report` 输出到 PR。

### 13.2 旧仓库渐进接入

1. Phase 1：`profile=observe_only`，只观察不拦；
2. Phase 2：`profile=enforce_l3`，new modules 强制有 L3；
3. Phase 3：核心模块切到 `full_harbor`，启用 strict L3 + DDT_MINIMAL。

## 14. 限制与未来演进

v1.0.2 明确承认的限制：

1. 语义正确性主要靠测试/审查，AI 审计只是辅助提示；
2. 严格 L3 + DDT 仍然需要团队文化支撑，Harbor 只是降低摩擦；
3. Diary 的价值高度依赖合理配置 `importance/visibility`，否则要么噪音、要么没人用；
4. 多语言适配、自动生成高质量测试、更多静态分析都属于 v1.1+ 的演进方向。
