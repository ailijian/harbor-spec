# Harbor-spec v1.0.0：主动上下文引擎设计蓝图

> 一句话定位：
> **Harbor-spec =「像 Git 管代码仓库一样，自动管理 vibe coding 的上下文仓库」**
> —— 以 L3 Docstring 为原子事实、以 DDT 测试为可执行规范、以 L2/Diary 为可计算视图，配合 CLI + Sync Engine + AI 规则，为 AI 驱动开发（vibe coding）提供一个**强一致、可回溯、可治理**的主动上下文层。

---

## 0. 设计宗旨与 Git 类比

### 0.1 设计宗旨

Harbor-spec v1.0.0 解决四个核心痛点：

1. **上下文漂移（Context Drift）**

   * 代码和“口头规范”脱节；
   * LLM 只读到部分上下文，输出不可控。

2. **文档“为人写”不适配 AI**

   * `/docs` 目录里一堆被遗忘的文档；
   * LLM 从不主动读，导致“凭空想象”。

3. **TDD 在 vibe coding 下落地困难**

   * 实际过程是：先让 AI 把代码写出来，再补测试；
   * 现实需求是：**如何从已经写好的代码与 Docstring 反向驱动测试**。

4. **团队级治理缺位**

   * 即使一个人用 Cursor+Rules 很自觉，
   * 其他只用 VS Code 的成员也可以轻松“绕过”所有约束。

### 0.2 与 Git 的类比心智模型

* Git 管理的是：**源码快照与提交历史**；
* Harbor 管理的是：**主动上下文（L3/L2/Diary）的快照与演进**。

对应关系可以这样理解：

| Git               | Harbor-spec v1.0.0                      |
| ----------------- | --------------------------------------- |
| 代码文件（.py/.ts/...） | L3 Docstring（代码内的契约注释）                  |
| `git status`      | `harbor status`（上下文是否“干净”）              |
| `git diff`        | `harbor diff context`（契约/L2/Diary diff） |
| `git log`         | `harbor log context`（上下文变更历史）           |
| commit 钩子 / CI 校验 | pre-commit 中的 `harbor sync` + CI 校验     |
| 分支策略              | Harbor 不直接管分支，但 context diff 可辅助审查      |

**类比结论**：

> Harbor 不取代 Git，而是站在 Git 之上，**管理“代码背后的规范与语义”**，并把它们变成可以被 AI & 工具消费的“上下文仓库”。

## 1. 核心概念与不变式（Invariants）

### 1.1 四层上下文模型

1. **L1 – Constitution（宪法）**

   * 位置：`/.cursor/rules/harbor-spec-L1-Constitution.mdc`
   * 内容：项目的“物理法则”和 AI 行为底线（技术栈、架构原则、DDT/确认循环规则等）。

2. **L2 – Anchor（锚点 / 模块 README）**

   * 位置：`/modules/<name>/README.md`
   * 由 Harbor 自动从 L3 解析生成，**只读视图**，不可手改。

3. **L3 – Atomic Fact（原子事实 / Docstring 契约）**

   * 位置：代码内部 Docstring（例如 `modules/auth/src/login.py`）；
   * 是行为与契约的 **单一事实来源（SSOT）**。

4. **L-Memory – Diary（开发日记 / 演进记忆）**

   * 结构化存储：`/specs/DEVELOPMENT_DIARY.jsonl`；
   * 可读镜像：`/specs/DEVELOPMENT_DIARY.md`（由 JSONL 渲染），只读视图。

### 1.2 关键不变式（必须长期成立）

1. **L3 代码 ↔ Docstring 强一致（Hard Invariant）**

   * 任何 L3 函数，只要签名或函数体改变，对应 Docstring 必须同步更新；
   * 仓库层通过 `harbor sync l3 --check` 强制校验；
   * **无论任何模式/配置，L3 不一致一律视为错误，阻塞提交/CI**。

2. **L2/Diary 只是 L3 的视图，不是事实源**

   * L2 README 与 Diary Markdown 都带有 `AUTO-GENERATED BY HARBOR` 头；
   * 真相源分别为：`.harbor/l3_index.json` 和 `DEVELOPMENT_DIARY.jsonl`；
   * 手动编辑 L2/Diary 的行为会被识别并给出警告/错误。

3. **Public API 必须有 DDT（Docstring-Driven Testing）覆盖**

   * Public 函数至少有一条正常路径 + 一条异常路径测试；
   * 测试通过 `@harbor_ddt_target(func="...", l3_version=N)` 绑定到 L3 契约版本；
   * 当 L3 版本号递增而测试未同步更新时，在 strict 模式下视为错误。

4. **Harbor 是“模块/路径级可配置”的**

   * 可以只对新模块、指定路径启用 Harbor 管控（gradual 采纳）；
   * 老 legacy 代码可以暂时只做观察，不阻塞。

## 2. 仓库结构与 .harbor 元数据

### 2.1 推荐目录结构（示意）

```text
.
├─ modules/
│   ├─ auth/
│   │   ├─ src/
│   │   │   ├─ login.py
│   │   │   └─ ...
│   │   ├─ tests/
│   │   │   ├─ test_login.py
│   │   └─ README.md          # L2，Harbor 自动生成
│   └─ billing/
│       └─ ...
├─ specs/
│   ├─ DEVELOPMENT_DIARY.jsonl  # L-Memory 真相源
│   └─ DEVELOPMENT_DIARY.md     # L-Memory 只读视图
├─ .harbor/
│   ├─ config.yaml
│   ├─ l3_index.json
│   ├─ diary_index.json
│   ├─ l2_meta.json
│   ├─ health.json
│   └─ cache/...
└─ .cursor/
    └─ rules/
       ├─ harbor-spec-L1-Constitution.mdc
       └─ harbor-spec-router.mdc
```

### 2.2 `.harbor/` 结构说明

* `config.yaml`：Harbor 全局配置与 profile；
* `l3_index.json`：所有受管函数的结构化 L3 索引；
* `diary_index.json`：Diary 按模块/文件/函数的倒排索引；
* `l2_meta.json`：L2 辅助信息（统计、机器字段），避免 README 抖动；
* `health.json`：最近一次 `harbor health` 的快照，用于 CI/Dashboard；
* `cache/`：解析缓存等临时信息。

## 3. 配置与 Profile：`.harbor/config.yaml`

### 3.1 示例配置

```yaml
schema_version: "1.0.0"

project:
  name: "awesome-service"
  language: "python"
  profile: "enforce_l3"    # observe_only | enforce_l3 | full_harbor

code_roots:
  - "modules/*/src"

test_roots:
  - "modules/*/tests"

l3:
  enabled: true
  # 默认纳入 Harbor 管控的路径（可用 glob），未列出的视为 legacy（仅观察）
  enabled_paths:
    - "modules/*/src"
  exclude_paths:
    - "legacy/**"

l2:
  enabled: true
  auto_regen: true

diary:
  enabled: true
  file: "specs/DEVELOPMENT_DIARY.jsonl"

sync:
  mode: "relaxed"             # relaxed | strict
  # 注意：L3 不一致在任何模式下一律视为错误

health:
  thresholds:
    min_public_ddt_coverage: 0.8
    max_context_debt: 10
```

### 3.2 Profile 语义

Harbor 提供三档「采纳档位」：

1. `observe_only`

   * 行为：

     * 解析 L3/L2/Diary 并提供健康报告；
     * **不阻塞任何提交**（包括 DDT、Diary、L2 等）；
     * 但 L3 不一致仍然会被标红提示（建议修复但不强制）。

2. `enforce_l3`

   * 行为：

     * **L3 同步错误 → 直接 fail**（无论 sync.mode）；
     * DDT / Diary / L2 相关问题仅 warning；
   * 适合：**第一阶段迁移**：先把 Docstring 文化立起来。

3. `full_harbor`

   * 行为：

     * 同时强制：

       * L3 强一致；
       * Public API 至少 `DDT_MINIMAL` 覆盖；
       * Diary 候选处理后 Context Debt 不超过阈值；
       * L2 README 生成无严重错误。
     * 一般搭配 `sync.mode: strict` 使用。

> 推荐实践：
>
> * 新/小项目：直接 `full_harbor + strict`；
> * 老/大仓库：先 `observe_only → enforce_l3 → full_harbor` 渐进演进。

## 4. L3 层：Docstring 作为原子事实

### 4.1 Docstring Schema 与 Tag 规范（Python）

示例：

```python
def login_user(username: str, password: str) -> Token:
    """用户登录。

    功能:
      - 校验用户凭证
      - 创建会话

    使用场景:
      - Web 登录入口
      - 内部服务调用禁止使用（请改用 service_login）

    依赖:
      - modules.account
      - modules.session

    @harbor.scope: public
    @harbor.idempotency: once

    Args:
      username (str): 用户名。
      password (str): 明文密码（TODO: 后续引入加盐哈希）。

    Returns:
      Token: 登录成功后的访问令牌。

    Raises:
      AuthError: 凭证错误。
      RateLimitError: 风控限流。
    """
```

要求：

* 风格：Google Docstring；
* 必填字段：

  * `Args / Returns / Raises`；
  * “功能 / 使用场景 / 依赖”（自然语言 + 结构化 tag 可解析）；
  * `@harbor.scope: public|internal`；
  * `@harbor.idempotency: pure|read-only|once|retriable`。

### 4.2 L3 索引模型：`.harbor/l3_index.json`

结构简化示例：

```jsonc
{
  "schema_version": "1.0.0",
  "functions": [
    {
      "id": "modules.auth.login.login_user",
      "file": "modules/auth/src/login.py",
      "name": "login_user",
      "scope": "public",
      "signature_hash": "sha256:...",
      "body_hash": "sha256:...",
      "docstring_hash": "sha256:...",
      "l3_version": 3,
      "idempotency": "once",
      "why_when": "仅 Web 登录使用，禁止内部服务。",
      "deps": ["modules.account", "modules.session"],
      "last_updated": "2025-11-10T12:34:56Z",
      "last_updated_by": "CA / AI",
      "provenance": {
        "commit": "abc123",
        "tool_version": "harbor-cli 1.0.0",
        "source": "ai"
      },
      "ddt_status": "DDT_MINIMAL"
    }
  ]
}
```

### 4.3 `harbor sync l3`：强一致检查与自动修复建议

#### 4.3.1 `--check`

* 扫描 `code_roots` 中受管路径，使用 Python AST + Adapter 提取所有函数；
* 对比 `l3_index.json`：

  * 新增函数无 Docstring → `L3_DOCSTRING_MISSING`；
  * 函数签名或 body_hash 变化，但 docstring_hash 未变 → `L3_DOCSTRING_OUT_OF_SYNC`；
  * Docstring 内容变了 → 视为契约更新，`l3_version` 应递增。
* 结果：

  * 如存在任一 `L3_DOCSTRING_*` 错误 → 退出码非零；
  * **不受 profile / sync.mode 影响**。

#### 4.3.2 `--apply`

* 在 `--check` 的基础上，帮开发者做“模板修复建议”：

  * 对无 Docstring 的函数：

    * 基于参数和返回类型生成一个最小模板；
  * 对签名变化：

    * 生成新模板，保留 WHY/WHEN 等旧字段；
* 不直接改文件，而是生成 patch 提示（或通过 IDE 插件辅助应用）。

## 5. DDT：Docstring-Driven Testing

### 5.1 定义与目标

> **DDT**：在 Harbor 范式下，每次 L3 函数改动遵循：
>
> 1. **先实现代码 + L3 Docstring（原子事务）**；
> 2. **从 L3 契约自动推导测试用例**；
> 3. 测试绑定到特定 `l3_version`；
> 4. L3 契约更新时，测试必须同步更新，否则在 strict 模式下视为不安全。

与传统 TDD 的区别：

* TDD：先写测试再写实现；
* DDT：**先写契约（Docstring），再从契约生成/更新测试**，更符合 vibe coding 实际流程。

### 5.2 测试与 L3 的绑定

示例测试标记：

```python
@harbor_ddt_target(
    func="modules.auth.login.login_user",
    l3_version=3
)
def test_login_user_valid_credentials():
    ...

@harbor_ddt_target(
    func="modules.auth.login.login_user",
    l3_version=3
)
def test_login_user_invalid_password_raises():
    ...
```

Harbor CLI 行为：

* 当 `l3_index` 中 `login_user.l3_version = 4` 时：

  * 若没有任何测试绑定到 `l3_version=4`：

    * `profile=enforce_l3`：warning；
    * `profile=full_harbor && sync.mode=strict`：fail。

### 5.3 DDT 等级与最低安全线

* `DDT_NONE`：无任何绑定测试；
* `DDT_MINIMAL`：至少 1 条正常路径 + 1 条异常路径；
* `DDT_FULL`：覆盖全部关键分支（未来扩展）。

**v1.0.0 要求：**

* 对 **Public API**：

  * `profile=full_harbor && sync.mode=strict` 下，若 DDT 状态 < `DDT_MINIMAL` → fail。

## 6. L2 层：自动生成的模块锚点

### 6.1 README 模板（自动生成）

示例（简化）：

```markdown
<!-- AUTO-GENERATED BY HARBOR 1.0.0. DO NOT EDIT MANUALLY. -->

# modules/auth 模块说明

## 1. 职责概述

用户认证模块，负责登录、登出、会话管理等。

## 2. 公共 API（Public）

| 名称        | 简要说明   | 使用场景                      | Idempotency | 依赖                     |
|-------------|------------|-------------------------------|------------|--------------------------|
| login_user  | 用户登录   | Web 登录入口；禁止内部调用   | once       | modules.account, session |
| logout_user | 用户登出   | 仅针对 Web 会话              | once       | modules.session          |

## 3. 内部函数（关键辅助）

...（可选）

## 4. 依赖关系

- 上游依赖：...
- 下游被依赖：...

## 5. DDT 覆盖概览（只读）

- 公共 API 总数：4
- DDT_MINIMAL 或以上：3
- 覆盖率：75%
```

### 6.2 生成流程：`harbor gen l2 --module modules/auth`

* 基于 `.harbor/l3_index.json` 过滤出该模块下的所有函数；
* 聚合 Public API 信息、依赖关系、DDT 状况；
* 渲染模板生成 README；
* 在 `auto_regen: true` 时，由 Sync Engine 自动调用。

### 6.3 手工编辑防护

* README 头部有 `AUTO-GENERATED` 标记；
* `harbor sync --ci` 时：

  * 若头部标记缺失或 README diff 无法用模板再现 → 提醒：

    > “README 似乎被手动编辑。请恢复或执行 `harbor gen l2` 重建。”

## 7. L-Memory：结构化 Diary 与索引

### 7.1 DiaryEntry 模型（JSONL）

```jsonc
{
  "id": "2025-11-07T10:00:00Z_auth_bugfix_001",
  "timestamp": "2025-11-07T10:00:00Z",
  "author": "CA / AI",
  "type": "bugfix",                  // feature | bugfix | refactor | chore | incident
  "modules": ["modules/auth"],
  "files": ["modules/auth/src/login.py"],
  "functions": ["modules.auth.login.login_user"],
  "summary": "修复 login_user 未捕获 DBError 导致 500 的问题。",
  "reason": "违反 L1 规则：API 不得返回 500。",
  "change": "在 login_user 中捕获 DBError 并转为 401。",
  "related_commits": ["abc123"],
  "related_issues": ["#42"],
  "tags": ["Auth", "DBError", "HTTP 500"],
  "breaking_change": false
}
```

* 存储：`specs/DEVELOPMENT_DIARY.jsonl`，一行一个对象；
* Markdown 视图：`specs/DEVELOPMENT_DIARY.md` 由 CLI 渲染生成，带 `AUTO-GENERATED` 头。

### 7.2 索引：`.harbor/diary_index.json`

```jsonc
{
  "schema_version": "1.0.0",
  "by_module": {
    "modules/auth": ["entry_id_1", "entry_id_2"]
  },
  "by_file": {
    "modules/auth/src/login.py": ["entry_id_1"]
  },
  "by_function": {
    "modules.auth.login.login_user": ["entry_id_1"]
  }
}
```

* 由 CLI 命令 `harbor diary rebuild-index` 或 Sync Engine 自动维护。

### 7.3 Diary 候选生成（Auto Draft）

当检测到以下情况之一时，Sync Engine 会生成 Diary 候选（需要 CA 确认）：

1. Public API 的 L3 WHY/WHEN / Raises 等关键字段有明显变更；
2. Public API 对应测试中，从 fail→pass 或 pass→fail 且涉及关键路径。

候选示例（内部结构）：

```jsonc
{
  "id": "auto_2025-11-10T12:03:00Z_auth_login_change",
  "timestamp": "2025-11-10T12:03:00Z",
  "author": "AI",
  "type": "bugfix_or_behavior_change",
  "modules": ["modules/auth"],
  ...
  "tags": ["Autogen", "Needs_CA_Review"],
  "breaking_change": false
}
```

CA 可以在 IDE / CLI 中：

* 接受并编辑 → 写入 JSONL；
* 标记为“本次无需记录”。

## 8. Sync Engine v1.0：事件 → Sync Plan → 执行

### 8.1 触发入口

1. 本地 watch（可选）：

   ```bash
   harbor watch
   ```
2. pre-commit：

   ```bash
   harbor sync --pre-commit
   ```
3. CI：

   ```bash
   harbor sync --ci
   ```

### 8.2 Sync Plan 结构

```jsonc
{
  "plan_id": "2025-11-10T12:00:00Z_sync_001",
  "changed_functions": [
    "modules.auth.login.login_user"
  ],
  "operations": [
    {
      "type": "update_l3_index",
      "targets": ["modules.auth.login.login_user"],
      "safety": "safe",
      "auto_apply": true
    },
    {
      "type": "regen_l2_readme",
      "targets": ["modules/auth"],
      "safety": "safe",
      "auto_apply": true
    },
    {
      "type": "update_diary_candidate",
      "targets": ["modules.auth.login.login_user"],
      "safety": "needs_ca",
      "auto_apply": false
    }
  ]
}
```

* `safe + auto_apply=true`：无须人工确认，可自动执行；
* `needs_ca`：生成候选，IDE/CLI 提示 CA 审查。

### 8.3 错误类别与处理策略（总结）

* `L3_PARSE_ERROR`：

  * relaxed：warning + 建议 `harbor doctor`；
  * strict：fail。
* `L3_DOCSTRING_MISSING/OUT_OF_SYNC`：

  * 任意模式：fail（Harbor 核心底线）。
* `L2_REGEN_FAILED`：

  * relaxed：warning，标记该 README 状态“不可用”；
  * strict：fail。
* `DIARY_INDEX_CORRUPTED`：

  * 自动尝试重建；
  * 失败则 warning + 建议 `harbor diary rebuild-index`。

## 9. CLI 命令族（v1.0.0 版）

### 9.1 初始化与配置

* `harbor init [--profile <name>] [--with-pre-commit] [--with-github-actions]`

  * 自动生成 `.harbor/config.yaml`、`.cursor/rules` 样板；
  * 可选生成 pre-commit、CI 模板。

### 9.2 同步与检查

* `harbor sync l3 --check|--apply`
* `harbor sync --pre-commit`
* `harbor sync --ci`

  * 入口统一调用 Sync Engine，执行 L3/L2/Diary 检查与同步。

### 9.3 状态与诊断

* `harbor status`

  * 当前分支/工作区的上下文变更摘要（类似 `git status`）。
* `harbor diff context [--against <ref>] [--module <path>] [--func <id>]`

  * 上下文层 diff（L3 契约 / L2 / Diary 摘要）。
* `harbor log context [--module <path>] [--func <id>]`

  * 上下文历史记录。
* `harbor health`

  * 输出 L3 同步率、Public DDT 覆盖、Diary debt 等指标；写入 `.harbor/health.json`。
* `harbor doctor`

  * 全项目诊断，输出可执行的修复建议。

### 9.4 开发者友好封装

* `harbor overview`

  * 等价于：综合 `status + health + doctor` 的一页总览。
* `harbor quickfix`

  * 自动尝试：

    * 为缺失 Docstring 的函数生成模板；
    * 修复可自动重建的索引；
  * 只在必须人决策时停下。

### 9.5 报告与 PR 集成

## 11. AI 集成：L1 宪法 & Router & Context API

### 11.1 确认循环模板（v1.0.0 固定版）

L1 宪法中规定：

> 在执行任何实质性改动（代码/Docstring/测试/Diary/L2/Harbor CLI）前，你必须使用如下格式输出“确认循环”：
>
> ```text
> 「确认循环 v1.0.0」
>
> 1. 任务理解：
>    - ...
>
> 2. 已加载上下文：
>    - L1：...
>    - L2：涉及模块 README ...
>    - L3：涉及函数/文件 ...
>    - Diary：涉及 DiaryEntry ...
>
> 3. 执行计划：
>    - 步骤1：...
>    - 步骤2：...
>
> 4. 影响范围与风险：
>    - ...
>
> 5. 需要 CA 决策：
>    - ...
>
> 请明确回复「确认执行」或「修改建议」。
> ```

### 11.2 Harbor Context API（逻辑接口）

提供给 Router 与 IDE/AI 的抽象调用：

1. `harbor.context.module_summary(module_path)`
2. `harbor.context.function_contract(func_id)`
3. `harbor.context.diary(id_or_module_or_func, since)`

Router 使用规则：

* 处理任务前 **必须**：

  * 通过 Context API 获取 module_summary / function_contract；
  * 根据需要查询最近 N 条 Diary；
* 在确认循环“已加载上下文”部分引用这些信息，而不是拍脑袋。

### 11.3 Router 行为纲要

* Debug 任务：

  * 解析用户提到的文件/函数 → 调用 `function_contract` + `diary`；
  * 只在需要时加载原始源码和 README。
* 新功能/重构：

  * 先加载相关模块 summary 和现有 Public API 契约；
  * 确认循环中陈述“拟新增/修改的 API 边界”。

## 12. 典型工作流（v1.0.0 视角）

### 12.1 绿地项目接入（新仓库）

1. 初始化：

   ```bash
   pip install harbor-spec-cli
   harbor init --profile full_harbor --with-pre-commit --with-github-actions
   ```
2. 第一轮开发：

   * 按 vibe coding + DDT 流程：AI 写代码+Docstring → 触发 DDT → 生成 L2/Diary；
3. 提交前：

   * `pre-commit` 中 `harbor sync --pre-commit` 保底校验；
4. CI：

   * 跑 `harbor sync --ci` + `harbor report`，在 PR 中展示上下文变更。

### 12.2 在旧仓库渐进采用

1. `harbor init --profile enforce_l3`（默认 gradual 模式）；
2. 只为新模块目录（例如 `modules/new_*`）开启 Harbor；
3. 定期看 `harbor health` 报告；
4. 当 L3 文化稳定后，逐步扩大 `enabled_paths`，最终切到 `full_harbor`。

### 12.3 Debug 场景

1. CA：

   > “login_user 间歇性返回 500，请排查。”

2. AI：

   * Router 调用 `harbor.context.function_contract` 与 `harbor.context.diary`，展示最近 bugfix 历史；
   * 在确认循环中描述现有契约（不应返回 500）与可疑点（DBError 未处理等）。

3. 修复后：

   * 更新代码+Docstring；
   * 触发 DDT 测试更新；
   * Sync Engine 自动更新 L3 index & L2 README；
   * 生成 Diary 候选，CA 核对后写入。

## 结尾：为什么可以叫 v1.0.0？

对照你一开始的目标，v1.0.0 已经系统性满足：

1. **L3 Docstring 100% 与代码同步**

   * 通过 `harbor sync l3` + pre-commit/CI + profile 约束，L3 不一致在任何模式下一律 fail。

2. **L2 自动生成 & 只读视图**

   * 从 `l3_index.json` 确定性生成；
   * `AUTO-GENERATED` 头防止手误污染。

3. **Diary 结构化 + 索引 + 自动候选**

   * JSONL + 索引 + 自动草稿；
   * Markdown 镜像方便人类。

4. **确认循环标准模板化 & AI Router 行为收紧**

   * 固定输出结构；
   * 强制先查 Harbor Context，再动手。

5. **DDT 概念清晰且可执行**

   * L3 驱动测试，测试与 `l3_version` 绑定；
   * Public API DDT_MINIMAL 作为 strict 模式硬门槛。

6. **接入体验 & 团队治理**

   * `harbor init` + profiles + gradual 采纳；
   * `status / health / doctor / overview / quickfix / report` 一整套 DX 友好的工具链。
